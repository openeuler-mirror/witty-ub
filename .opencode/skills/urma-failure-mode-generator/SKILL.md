# urma-failure-mode-generator

## 目标

从 URMA 仓库源码中提取故障模式，生成：

- `/var/witty-ub/failure-modes/urma_failure_modes.md`

输出必须参考 `examples/failure-example.md` 的标题层级、字段、缩进和“向下级匹配”风格。优先保证故障对象和故障粒度准确，其次再做业务阶段归类。

## 输入

- `source_path`：必选，URMA 源码根目录或待分析目录。
- `callstack_path`：必选，函数调用栈文件。优先支持 `callstack.json` 的 `nodes`/`edges` 结构；若是文本，尽量抽取 `caller -> callee`、`caller calls callee` 等关系，无法可靠解析时说明限制并只使用可确认关系。

执行时还必须读取：

- `examples/failure-example.md`：输出格式基准。
- `references/additional_info.md`：部分函数的故障原因和解决办法补充。该文件缺失时继续生成，但结果中不要编造对应解决办法。

## 分析对象

以仓库中所有包含 `URMA_LOG_ERR` 错误日志输出的函数为基本分析对象，不限于公开 `urma_` 接口。包括 `static` 函数、内部 helper、回调函数、ops 表目标函数、provider/driver 实现函数。

只有函数体内直接出现 `URMA_LOG_ERR` 时，才纳入故障模式分析。一般来说，输出错误日志的分支会返回某个错误码；错误码、`NULL`、`false`、`-1` 等返回值用于辅助解释该日志分支，不再单独扩大分析对象范围。

扫描时重点识别：

1. `URMA_LOG_ERR` 所在函数、分支条件和日志关键字。
2. 同一分支或紧邻错误处理路径中的返回值，例如负 errno、非零错误码、失败枚举、`NULL`、`nullptr`、`false`、`-1`。
3. 日志分支中的参数校验、状态校验、资源检查和下游返回值检查。
4. 带 `URMA_LOG_ERR` 的公共跨态、命令下发、provider/driver 调用出口，例如封装 `ioctl`、`cmd`、`tlv`、`URMA_CMD`、`urma_cmd_t`、`urma_cmd_hdr_t`，或记录 `ioctl failed`、`kdrv_err`、`URMA_KERNEL_DRV_ERRNO`、`cmd:%u`。

不要只分析公开 API；但没有 `URMA_LOG_ERR` 的函数默认不作为独立故障模式对象。它们只作为上下游原因分析、错误码来源或 ops 分发目标参考。

## 故障粒度

一条 `URMA_LOG_ERR` 日志输出对应一个故障模式。该日志分支上的错误码或失败返回值是此故障模式的属性和现象补充，不再把无日志错误返回点单独拆成故障模式。

可以合并的唯一情况：同一个函数体内，分支条件、关键日志、错误码/返回值和失败语义完全一致。不同函数、不同分支、不同返回值、不同日志不得合并。

命名不要使用“分支1/分支2”，也不要在可区分原因时退化成 `<函数名> 执行失败`。必须结合日志内容、触发条件、失败对象、下游函数、错误码和上下文动作起更精准的名字。

命名优先级：

1. 优先从 `URMA_LOG_ERR` 日志格式字符串中提取稳定失败动作或失败对象，例如 `query eid`、`open urma cdev`、`ioctl`、`import jfr`、`create jetty`。
2. 日志不足以区分时，结合触发条件，例如 `dev_fd < 0`、`urma_query_eid(...) != 0`、`ctx == NULL`。
3. 如果该日志分支检查下游函数返回值，名称中体现下游函数或业务动作，例如 `urma_create_context 查询EID失败`。
4. 如果该日志分支检查系统资源、设备文件、fd、权限、内存或驱动返回值，名称中体现具体资源或失败类型，例如 `urma_create_context 打开cdev设备失败`。
5. 如果同一函数下多条日志都会返回相同错误值，也必须按日志语义和触发点区分命名，不能只写相同的 `<函数名> 执行失败`。
6. 只有日志文本、触发条件和上下文都无法提供更具体语义时，才可使用 `<函数名> 执行失败` 作为兜底。

推荐格式示例：

- `<函数名> <参数名> 参数非法`
- `<函数名> 调用 <下游函数名> 返回错误码 <错误码>`
- `<函数名> 返回错误码 <错误码>`
- `<函数名> ioctl调用失败`
- `<资源名> 创建/查询/导入/注册/销毁失败`
- `urma_create_context 查询EID失败`
- `urma_create_context 打开cdev设备失败`

例如同在 `urma_create_context` 中：

- 日志 `Failed to query eid.` 且触发条件为 `urma_query_eid(dev, eid_index, &eid) != 0`，应命名为 `urma_create_context 查询EID失败`，不要命名为 `urma_create_context 执行失败`。
- 日志 `Failed to open urma cdev with path %s, dev_fd: %d` 且触发条件为 `dev_fd < 0`，应命名为 `urma_create_context 打开cdev设备失败`，不要命名为 `urma_create_context 执行失败`。

## 直接故障与关联故障

这是本技能最重要的边界。

### 可直接挂载到函数节点下的故障

只有当前函数实现中直接体现的故障，才能作为该函数节点的直属下级：

1. 当前函数体内直接打印的 `URMA_LOG_ERR` 日志。
2. 当前函数体内 `URMA_LOG_ERR` 所在错误分支的参数校验、状态校验或资源检查失败。
3. 当前函数体内检查下游函数返回值后，自己打印 `URMA_LOG_ERR`，并转换错误码、设置状态或返回错误值。

第 3 类的故障属于当前函数的错误处理分支。故障原因可以引用下游函数名，但故障现象必须描述当前函数可观察到的 `URMA_LOG_ERR` 日志和返回值，不得复制下游函数内部日志。

### 不可直接挂载的关系

以下关系不能把下游函数内部故障直接挂到上游函数节点下：

1. 普通函数调用关系。
2. 调用栈可达关系。
3. 函数指针、回调、注册表分发关系。
4. 全局 `ops` 结构体、provider/driver ops 表、设备 ops 表中的指针分发关系。
5. 公共跨态/驱动出口被多个上游调用的关系。

这些关系不能直接决定故障类目名称。故障树类目应优先使用业务语义，例如：

- `初始化失败`
- `建链失败`
- `资源创建失败`
- `资源查询失败`
- `资源导入/注册失败`
- `数据收发失败`
- `资源销毁/清理失败`
- `设备/驱动交互失败`
- `其他URMA故障`

调用关系、调用栈可达关系、ops 分发和函数指针分发只用于说明上下游关系，并通过 `下级故障` 编号引用已经独立输出的函数节点或故障节点，不能复制被引用节点的内容。只有在无法归入明确业务语义时，才可使用较泛化的 `其他URMA故障`，并在节点原因中说明它来自调用或分发链路。

## 上下游关系整理

先按函数内部直接故障建立函数节点，再用调用栈和源码关系补充树上的上下游引用。

1. 函数节点下只放该函数直接故障。
2. 如果上游函数只是调用下游并透传返回值，且没有自己的日志、错误码转换、参数校验或额外状态处理，不为上游新增“调用下游失败”故障。
3. 如果上游函数检查下游返回值并产生自己的日志或错误返回，则输出上游自己的故障模式；原因里可写“下游 `<callee>` 失败后，上游 `<caller>` 返回/记录该错误”。
4. 公共跨态/驱动出口函数只输出一次。多个上游入口触发它时，在该出口节点的故障原因或对应业务类目中说明上游范围。
5. ops 分发关系不作为默认类目名。例如 `urma_xxx` 入口通过 `g_urma_ops->create_*` 分发到实现函数时，入口节点不能直接挂实现函数内部叶子；应按该实现函数实际业务语义归入资源创建、资源查询、数据收发、设备/驱动交互等类目，并用 `下级故障` 表达上下游引用。

## 非叶节点也可以有原因

不要机械地把所有非叶节点都写成“向下级匹配”。

如果某个函数节点或中间节点自身已经能说明故障原因、表现或解决办法，同时它又因为实现中调用下游函数而存在下级故障，可以在该节点写具体内容。例如：

- 当前函数记录了“下游返回失败”的 ERROR 日志，可以在该函数节点写当前层可观察的日志和原因。
- 下游函数内部还有独立故障时，下游作为下级或关联节点继续展开。

只有纯分类节点、纯关联节点、或必须继续向下才能定位根因的节点，才写：

- `故障现象：向下级匹配。`
- `故障原因：向下级匹配。`
- `解决方法：向下级匹配。`

## 叶子故障字段

每个叶子故障必须包含：

```markdown
* 故障编号：urma_xxx
* 下级故障：[]
* 故障现象：
    * 关键日志：匹配xxx
    * 日志路径：URMA_LOG_PATH
* 故障原因：xxx
* 解决办法：无
```

日志路径规则：

1. 用户态 URMA 日志默认写 `URMA_LOG_PATH`。
2. 内核、驱动或 dmesg 相关日志写 `URMA_LOG_PATH 或者dmesg`。
3. 若 `URMA_LOG_ERR` 分支同时返回错误码、`NULL`、`false` 或 `-1`，可在 `关键日志` 或 `故障原因` 中补充该返回值；不要生成独立的“无日志错误返回”故障。

故障原因必须尽量基于源码判断：参数非法、状态不匹配、资源不存在、权限不足、超时、内存不足、设备能力不支持、下游调用失败、驱动返回错误等。证据不足时用“可能由于”或“通常表示”，不要编造确定原因。

解决办法默认写 `无`。命中 `references/additional_info.md` 的相关函数时，按该文件填充原因和/或解决办法；该文件写“当前不会触发”等内容时也保留原意。

## 输出树结构

顶层固定：

```markdown
## URMA故障
```

建议层级：

1. 一级故障按业务阶段或故障语义归类，例如初始化、建链、资源创建、资源查询、导入/注册、数据收发、销毁清理、设备/驱动交互、其他URMA故障。不要把 `调用关系`、`ops分发`、`间接分派` 这类实现关系直接当作业务故障类目。
2. 二级故障优先是函数节点，标题中应包含函数名。
3. 三级及以下是该函数体内直接故障，或进一步的函数节点/关系节点。
4. 每个节点都必须有 `故障编号` 和 `下级故障`。
5. 编号从 `urma_001` 开始，按文档出现顺序连续递增。
6. `下级故障` 只写直属下级编号；叶子写 `[]`。
7. 如果某个业务类目需要表达调用、调用栈、ops 或函数指针带来的上下游关系，使用 `下级故障` 引用已经独立输出的函数节点或故障节点，不得复制其内容。

若没有识别到任何故障，仍生成：

```markdown
## URMA故障
### 1 未识别到明确故障模式
* 故障编号：urma_001
* 下级故障：[]
* 故障现象：
    * 关键日志：未在输入源码中识别到URMA_LOG_ERR错误日志输出
    * 日志路径：无
* 故障原因：无
* 解决办法：无
```

## 执行流程

1. 校验 `source_path`、`callstack_path` 可访问。
2. 读取 `examples/failure-example.md` 和 `references/additional_info.md`。
3. 解析调用栈，得到 `caller -> callee`、上游集合、下游集合。
4. 扫描 C/C++ 源码文件，定位所有函数定义和函数体。
5. 只对每个包含 `URMA_LOG_ERR` 的函数识别：
   - `URMA_LOG_ERR` 日志。
   - `URMA_LOG_ERR` 所在分支的参数校验、状态校验、资源检查或下游返回值检查。
   - `URMA_LOG_ERR` 分支对应的非成功返回值，包括错误码、`NULL`、`nullptr`、`false`、`-1`。
   - 带 `URMA_LOG_ERR` 的 `ioctl`、`cmd`、`tlv`、provider/driver 调用出口。
6. 对每个包含 `URMA_LOG_ERR` 的函数建立“函数节点 + 直接故障叶子”。
7. 根据调用栈、源码调用、ops 表和函数指针关系补充业务类目下的上下游引用；关系本身不是默认类目名。
8. 应用 `additional_info.md`：相关叶子命中函数名时补充原因和解决办法；未命中时解决办法为 `无`。
9. 按 `examples/failure-example.md` 的风格生成 `/var/witty-ub/failure-modes/urma_failure_modes.md`。
10. 生成后复查：
    - 所有带 `URMA_LOG_ERR` 的函数是否已覆盖。
    - 每条 `URMA_LOG_ERR` 日志输出是否对应一个故障模式。
    - 函数节点下是否只挂当前函数直接故障。
    - 调用关系和 ops 分发是否只作为上下游引用，没有被误写成业务故障类目。
    - 带 `URMA_LOG_ERR` 的公共跨态/驱动出口是否只输出一次。
    - 所有编号是否连续，`下级故障` 是否只引用直属下级。
    - 叶子是否都有故障现象、故障原因、解决办法。
    - 同一函数下多个叶子是否已按日志内容、触发条件和失败对象区分命名，避免重复使用 `<函数名> 执行失败`。

## 质量要求

1. `URMA_LOG_ERR` 覆盖完整性优先于归纳漂亮。
2. 不跨函数合并故障。
3. 不把下游内部故障复制到上游函数下。
4. 不把 ops 分发目标的内部故障直接挂到分发方下。
5. 不把公共驱动出口重复挂到多个上游下。
6. 不用“分支1/分支2”命名故障；同一函数内可区分原因的故障不能都命名为 `<函数名> 执行失败`。
7. 不编造源码、日志、配置项或解决办法。
8. 结果文件不加入分析过程、TODO、数据来源说明或调试信息。
