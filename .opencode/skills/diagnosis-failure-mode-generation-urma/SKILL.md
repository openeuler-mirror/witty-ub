# diagnosis-failure-mode-generation-urma

## 目标

根据 URMA 组件的源码和函数调用关系，生成对应的故障模式树。故障模式树以 URMA 组件的函数调用关系为参考，以源码中各个函数内部的 ERROR 日志输出为单位，覆盖整个源码仓的故障发生点。你需要 URMA 组件的源码仓路径和函数调用关系作为输入，输出指定格式的故障模式树。

## 输入

- URMA 组件的源码仓路径
- URMA 组件的函数调用关系：默认使用./references/urma_callstack.json文件的数据，格式如下：
```json
{
    "nodes": [
        {
            "name": "functionA",
            "component": "liburma"
        },
        {
            "name": "functionB",
            "component": "liburma"
        }
    ],
    "edges": [
        {
            "src": "functionA",
            "dst": "functionB"
        }
    ]
}
```

## 输出

- 生成的故障模式树以markdown格式输出，基础模板说明参考./references/failure_mode_tree_example.md文件，输出路径为./output/urma_failure_mode_tree.md
- 故障模式树的每个节点对应一个函数中的一个 ERROR 日志输出点（URMA_LOG_ERR日志宏），节点内容包括以下标题和字段：
    - **故障名称**：作为节点标题，格式为“函数名 故障模式概述”，其中函数名为该节点对应的函数名称，故障模式概述为该节点对应的 ERROR 日志输出点的日志内容进行概括后的描述，不能简单抽取代码或日志内容，需要结合业务逻辑进行合理总结
    - **故障现象**：参见failure_mode_tree_example.md中的说明和示例，对 URMA 组件需要给出查看该日志的日志文件路径和识别该日志的关键字，不得新增别的字段；日志路径暂时定为环境变量URMA_LOG_PATH
    - **故障原因**：参见failure_mode_tree_example.md中的说明和示例，需要体现该函数的作用和该故障模式发生的具体的直接原因，不能仅体现代码字面量或很宽泛的描述；对于./references/function_additional_info.md中有说明的函数，需结合说明内容进行填写
    - **解决办法**：参见failure_mode_tree_example.md中的说明和示例，对 URMA 组件默认填写“无”；对于./references/function_additional_info.md中有说明的函数，需结合说明内容进行填写
    - **故障编号**：按顺序对所有故障节点进行编号，格式为`urma_xxx`，其中`xxx`是从001开始的三位数
- 无需增加别的字段或补充信息，不用输出故障发生的源码位置

### `故障名称`要求

故障名称必须体现“函数动作 + 失败对象/条件 + 失败后果”，禁止使用以下泛化短语作为故障概述：
- URMA 内部处理失败
- 资源创建流程失败
- 资源查询失败
- 参数或对象状态校验

例子：

- 不推荐：urma_get_device_list 资源查询失败
- 推荐：urma_get_device_list 打开 URMA 设备类目录失败导致设备列表无法枚举
- 不推荐：urma_tlv_ioctl 驱动 ioctl 命令执行失败
- 推荐：urma_tlv_ioctl TLV 命令下发内核驱动失败导致用户态资源操作中断

### `故障原因`要求

#### 日志点上下文

对每个 URMA_LOG_ERR 日志输出点，必须结合以下内容进行分析：
- 所在函数名
- 所在文件和行号
- 日志完整文本
- 日志所在的最近 if/else/错误分支条件
- 日志前后 10-20 行代码
- 当前分支内的返回值、errno、ret、资源对象名
- （若有）当前函数中与该错误分支相关的下层调用

#### 故障原因撰写要求

1. 故障原因必须解释触发该日志的直接原因，不得只写“依赖的参数、资源状态或下层调用结果不满足继续执行条件”这种宽泛的描述，可以结合日志文本和上下文对原因进行翻译和总结，但不能直接抽取代码或日志的字面内容。
2. 若日志点位于 if 分支中，需要把 if 条件翻译成业务原因，但不要直接输出if语句的字面内容
    - `ctx == NULL`：调用方未传入有效 URMA context
    - `ops == NULL || ops->xxx == NULL`：provider 未提供对应操作实现
    - `ret != 0`：下层资源创建/驱动命令返回失败
    - `errno`：系统调用失败，需说明对应文件、fd、目录或 ioctl 对象

#### 高频日志专项规则

- `Invalid parameter`：
    - 必须结合 if 条件指出具体无效对象，如 ctx、dev、ops、jfs、jfr、jetty、seg、wr、sgl、tjetty，不得只写“参数无效”。
- `Failed to alloc args`：
    - 必须说明分配的是哪个命令参数、资源参数或临时结构，以及失败会阻断哪个 URMA 操作。
- `ioctl failed`：
    - 必须说明 ioctl 对应的 URMA_CMD 命令语义，如创建 context、注册 segment、导入 jetty、查询 tp list 等。
- `Failed open/read/parse sysfs`：
    - 必须说明读取的是设备、EID、端口、能力或 cdev 路径信息。

## 操作步骤

### 步骤一：需求理解

阅读 URMA 组件的源码和参考文档，确保你理解了上述输入和输出中的所有内容。

### 步骤二：故障模式树生成

1. 分析 URMA 组件的源码，定位所有使用 URMA_LOG_ERR 日志宏输出错误日志的函数和代码位置
2. 结合顶层故障模式节点语义，对所有故障点进行归纳总结，构建符合要求的故障模式树结构
3. 根据每个故障点的代码上下文和业务逻辑，撰写符合要求的故障名称、故障现象、故障原因和解决办法
4. 将生成的故障模式树以markdown格式输出到./output/urma_failure_mode_tree.md文件中

#### 函数调用关系到故障模式树的映射规则

1. 函数调用关系仅作为故障模式树结构骨架的参考信息，并不代表故障模式本身的上下游关系。函数调用关系和故障模式树是两条线：调用关系描述函数之间“谁调用谁”，故障模式树描述 ERROR 日志输出点所代表的故障模式之间如何归类、承接和展开
2. 构建过程中可以临时引入“函数节点”作为桥梁节点。函数节点用于把分散在不同函数中的故障模式连接成可构建、可遍历的树结构，但函数节点不是最终故障模式树节点，也不在最终 markdown 中输出
3. 每个 ERROR 日志输出点独立生成一个故障模式节点。即使多个 ERROR 日志输出点位于同一个函数中，也应生成多个并列的故障模式节点；这些故障模式节点属于该函数，但不自动继承该函数所有被调函数作为下级
4. 被调函数只表示当前函数的下游函数，不表示当前函数内某个 ERROR 日志输出点的下游故障。例如某函数内有两个 URMA_LOG_ERR 日志点，同时调用了 functionA 和 functionB，则这两个被调函数只是该函数的下游函数，不能直接挂到这两个日志点生成的故障模式节点下面，除非源码业务逻辑明确表明某个日志点由该被调函数故障承接或展开
5. 推荐按以下中间结构构建故障模式树：
    - 先按函数调用关系构建临时函数骨架，边为“调用函数 -> 被调函数”
    - 再把每个函数内的 ERROR 日志输出点生成为故障模式节点，并挂到对应的临时函数节点下
    - 对没有 ERROR 日志但出现在调用链中的函数，保留为临时桥梁节点，用于连接其上下游函数
    - 对不存在于函数调用关系中但包含 ERROR 日志的函数，创建临时独立函数节点并挂载其故障模式节点
6. 生成最终故障模式树时，必须删除所有临时函数节点，并对因此断开的故障模式节点进行提升：
    - 如果函数节点的上游路径中存在可输出的故障模式节点，则将该函数节点下可输出的故障模式节点提升为这些上游故障模式节点的下级
    - 如果函数节点的上游路径中没有可输出的故障模式节点，则将该函数节点下可输出的故障模式节点提升为顶层故障模式节点，或挂到合适的业务语义顶层节点下
7. 最终故障模式节点之间的上下级关系需要结合函数调用骨架、源码控制流、错误传播路径和业务语义综合判断。只有当下游函数的 ERROR 日志确实是在当前故障模式的原因链、处理链或展开链上时，才把下游函数中的故障模式节点作为当前故障模式节点的下级

## 质量自检

1. 生成的故障模式树需要覆盖 URMA 组件源码中所有带有 ERROR 日志输出的函数，若某个函数不存在于函数调用关系中，仍需将其作为一个独立的节点添加到故障模式树中
2. 生成的故障模式树需要满足输出说明中规定的格式要求，且每个节点的内容需要合理且符合 URMA 组件的业务逻辑
3. 生成的故障名称、故障原因需要能够体现故障的本质和业务含义，便于用户理解，不应简单重复或抽取代码或日志的字面量，也不应简单描述为“xxx函数故障”
4. 顶层故障模式节点需体现业务语义，此类故障节点对应failure_mode_tree_example.md中需要向下级匹配的节点，如：
    - `初始化失败`
    - `建链失败`
    - `资源创建失败`
    - `资源查询失败`
    - `资源导入/注册失败`
    - `数据收发失败`
    - `资源销毁/清理失败`
    - `设备/驱动交互失败`
    - `其他URMA故障`
5. 其他故障模式节点均需要对应到具体函数的 ERROR 日志输出点，不应简单总结为“xxx函数故障”并向下级匹配
6. 是否将function_additional_info.md里部分函数的补充信息体现在故障模式树中
7. 不能把`UNKNOWN`、`__attribute__`、`defined`等预处理相关的错误分支生成故障模式节点，需修正为对应的函数调用错误分支
