# failure-mode-generation-ubsocket

## 目标

根据 UBSOCKET 组件的源码生成对应的故障模式树。故障模式树以 UBSOCKET 组件的同步函数调用关系和异步数据处理关系为参考，以源码中各个函数内部的 ERROR 日志输出为单位，覆盖整个源码仓中指定范围的故障发生点。你需要 UBSOCKET 组件的源码路径作为输入，输出指定格式的故障模式树。

## 输入

- UBSOCKET 组件的源码路径

禁止参考旧结果，包括项目中已存在的旧产物、git 历史提交和 `/tmp` 中存在的临时文件，必须重新调用脚本和skill进行分析

## 输出

- 生成的故障模式节点以 JSON 格式输出，输出路径为`./data/ubsocket/ubsocket_failure_mode.json`
- 除四个公共 API 对应的根节点外，每个故障节点对应一个函数中的一个 `UBS_VLOG_ERR/UBS_SLOG_ERR` 日志输出点，节点内容仅包括以下标题和字段：
    - **故障编号**：统一使用`ubsocket_xxx`格式；四个根节点固定为`ubsocket_001`至`ubsocket_004`，其余具体故障节点从`ubsocket_005`开始按顺序编号
    - **故障名称**：该字段是节点标题，是对该故障模式的高度概括
    - **故障现象**：通过日志关键字识别故障现象，需给出识别该日志的关键字
    - **故障原因**：故障模式对应具体故障原因，如故障还需向下级故障匹配，无法定位到根因，填写“向下级匹配”
    - **解决办法**：故障模式对应具体解决方法，默认填写“无”
    - **函数名**：调用 `UBS_VLOG_ERR/UBS_SLOG_ERR` 日志宏的函数，只填写`find_ubsocket_log_err.py`脚本输出的裸函数名
    - **文件名**：日志宏所在的源码裸文件名，根据`find_ubsocket_log_err.py`脚本输出的`file`字段填写，不得携带目录路径

### `故障名称`要求

1. 推荐风格为“xxx（操作）时yyy（故障原因概括）”，如“初始化xxx时参数无效”
2. 不得直接出现函数名、日志原文，必须根据函数的作用和日志内容进行概括

### `故障现象`要求

1. 需要匹配到所有的关键字，关键字来源如下：
    - 错误日志字面量，如：匹配 `Provider Bond register ops failed`
    - 如果有格式占位符，如`%d`、`%s`，需要以这样的占位符为分割，将前后的所有字面量作为关键字，如：依次匹配 `Failed to create bondp comp, dev_name:`、`, eid_idx:`
2. 关键日志最终输出格式为：依次匹配`关键字1`、`关键字2`

### `故障原因`要求

1. 根据 if 条件或下层函数调用的语义总结产生该故障的直接原因，最好是结合本函数的作用
2. 建议在故障名称的基础上扩写，如“初始化A时参数无效”可扩写为“初始化A时传入的参数B无效，导致无法完成初始化操作”

### `函数名`要求

1. `函数名`字段只允许填写裸函数名，不得携带类名、结构体名或命名空间限定符，字段值中不得出现`::`。
2. 即使源码、调用链或其他分析结果使用全限定名，也必须在写入最终 JSON 前去掉所有限定符，只保留最后一级函数名。

### `文件名`要求

1. `文件名`字段只允许填写源码裸文件名，不得携带目录路径。例如脚本输出的`file`为`core/umq/umq_data_rx_ops.cpp`时，`文件名`填写其最后一级`umq_data_rx_ops.cpp`。
2. 具体故障节点填写物理日志点所在文件；聚合节点的多个物理日志点必须位于同一个裸文件名，否则不得用单个`文件名`掩盖歧义，应重新检查节点聚合是否合理。
3. 四个公共 API 根节点没有物理日志点，`文件名`填写对应`SocketBase`公共 API 定义所在的`ubsocket_socket.h`。

### 故障聚合要求

1. 对于同一个函数中的多个 `UBS_VLOG_ERR/UBS_SLOG_ERR` 日志点，如果它们的日志内容完全相同（全字匹配），需要将它们聚合成一个故障节点。
2. 在四个公共 API 的同步和异步路径之间进行全局去重。同一个日志故障即使同时属于多个根节点的处理路径，也只生成一次、只分配一个故障编号；在关系图中允许多个上游节点指向这个共享故障节点，禁止为不同根节点复制内容相同但编号不同的具体故障节点。

## 故障模式树结构

故障模式节点分为公共 API 根节点和具体故障节点。具体故障节点不预先划分为中间节点或叶子节点，而是由`failure_mode_tree.json`中的下游关系决定：

- value 包含下游故障编号的具体故障节点是中间节点
- value 为空数组`[]`的具体故障节点是叶子节点

`ubsocket_failure_mode.json`负责保存全局唯一的节点定义，`failure_mode_tree.json`负责保存节点之间的有向下游关系。一个具体故障节点可以同时位于多个公共 API 的同步或异步路径中，也可以连接到其他具体故障节点，因此节点关系实际允许形成包含多层中间节点的有向图，而不是固定两层的树。

关系图中的具体故障节点边是**故障因果传播关系**，不是普通函数调用关系。`A: [B]`表示故障节点 A 所在日志点会在 B 所代表的下游故障通过同步返回值、状态码、异步数据对象或等价状态传播时触发。仅有“A 所在函数调用了 B 所在函数”这一事实，不能生成故障边。

公共 API 根节点没有物理日志点，是唯一允许表达归属关系的节点。根节点到具体节点的边除表示 API 失败路径上遇到的首个日志节点外，还可以表示：该日志属于 API 产生的数据对应的异步处理路径，或该日志失败被吞掉但在该 API 功能路径中可观测。此类根节点边不保证当次 API 调用返回失败。

### 顶层故障模式节点

顶层故障模式作为故障模式的类别呈现，体现 UBSOCKET 组件的功能模块，其故障现象、故障原因和解决办法均填写“向下级匹配”。四个公共 API 及其根节点编号固定为：

- `ubsocket_001`：连接发送失败，对应公共 API `SocketBase::Connect`
- `ubsocket_002`：连接接收失败，对应公共 API `SocketBase::Accept`
- `ubsocket_003`：数据读取失败，对应公共 API `SocketBase::ReadV`
- `ubsocket_004`：数据写入失败，对应公共 API `SocketBase::WriteV`

你需要从这几个公共 API 出发，结合同步函数调用关系、异步数据处理关系和日志输出点，构建完整的故障模式树。分析范围包括公共 API 的同步调用链，以及由 API 提交的数据、请求、缓冲区或状态触发的后台线程、事件循环、回调、定时轮询和队列消费路径。不在同步调用链中，且无法通过具体数据对象或状态证明与公共 API 存在异步来源或异步影响关系的日志点，不纳入分析和输出。

不得根据函数名称、业务用途或人为分类排除调用链中的函数。只要函数位于公共 API 的实际同步调用路径，或具有已证实的异步数据关系，就必须逐个分析其中的 ERROR 日志。函数是否用于初始化、重试、回滚、清理、刷新、解绑、销毁或析构，不影响其范围判定。

### 具体故障模式节点

具体故障模式节点对应日志输出点所表示的故障模式，其故障现象、故障原因和解决办法均填写具体内容。具体故障节点可能是中间节点，也可能是叶子节点；不要仅因它不是公共 API 根节点就将其视为叶子节点。

所有具体故障节点共用同一个编号空间，从`ubsocket_005`开始按顺序编号，格式为`ubsocket_xxx`，不归入任何根节点的编号命名空间。不得使用`ubsocket_001_001`、`ubsocket_002_001`等带根节点前缀的分级编号。

同步或异步处理链中没有对应日志故障的函数仅用于推导故障传播关系，不单独生成故障节点。只有确认该函数把某个下游失败继续返回，或通过共享数据、socket 状态、队列状态等价传播时，才能跳过该函数，将产生错误日志的最近上游节点连接到该失败路径上最近的下游故障节点。若下游失败被忽略、恢复、转换为成功，且未产生可供后续 API 检查的等价状态，则不得连接到上游具体日志；符合“失败被吞掉但日志可观测”条件时，只能由相关公共 API 根节点归属。

## 故障关系判定原则

必须逐个错误日志点分析，禁止把函数级调用图直接投影为故障节点关系。同一函数内的不同日志点通常具有不同的触发条件和下游集合。

| 类型 | 判定 | 下游关系 |
| --- | --- | --- |
| 一对多 | 一个日志点检查某个子调用的失败返回；该失败返回可能由子调用链中的多个具体故障点产生 | 该日志节点连接到这些失败路径上最近的多个下游故障节点 |
| 一对零 | 日志由本函数自身的参数、状态、资源或本地操作失败触发，与下游调用的失败返回无数据或控制依赖 | 该日志节点的 value 为`[]` |
| 零对多 | 中间函数没有错误日志，只把子调用失败继续返回；更上层函数根据这个传播结果记录错误日志 | 跳过无日志中间函数，把符合`上游节点归属判定`的上游日志节点连接到对应的下游故障节点 |
| 失败被吞掉但日志可观测 | 子函数记录错误日志，返回void或返回错误码但调用方、后台线程、事件循环或回调忽略、覆盖该返回值或转换为成功 | 不连接到任何虚假的上游具体日志；由相关公共 API 根节点直接连接该日志节点，节点自身仍按其日志触发条件分析下游 |
| 异步一对多 | API 提交的数据在后台处理时发生错误，该错误通过同一数据对象或共享状态触发后续具体日志 | 后续具体日志节点连接到异步失败路径上最近的多个故障节点 |
| 异步零对多 | 异步中间函数没有错误日志，但通过同一数据对象或共享状态继续传递错误 | 跳过无日志异步函数，把后续具体日志连接到最近的异步故障节点 |
| 异步可观测但被吞掉 | 后台日志记录失败，但调度入口忽略返回值，且没有改变后续 API 检查的状态 | 由异步数据来源所属的公共 API 根节点直接连接 |

对每个日志点执行以下分析：

1. 读取日志所在函数及必要的被调函数源码，定位日志所在的`if/switch/catch/goto`分支、提前返回路径或失败清理路径。
2. 从日志触发条件向后追溯变量定义和赋值，判断其来源是本函数自身产生，还是某个具体调用点的返回值、输出参数、错误码或由其转换得到的状态。变量改名、布尔化、错误码映射和无日志包装函数不切断传播关系。
3. 只有在下游调用的失败结果能够沿实际控制流到达该日志点时，才标记为“下游透传”。函数内存在某个调用、调用与日志相邻、或二者位于同一函数，均不能单独作为证据。
4. 对每个已确认的下游透传调用，沿对应失败返回路径向下查找，并只选择该路径上**最近的具体故障节点**作为直接下游。若最近节点本身还透传更深层故障，由该最近节点继续连接下一层，禁止上游节点越过它连接所有后代。
5. 若被调函数在该失败路径上没有日志但继续调用并传播更深层失败，则继续向下穿透无日志函数；若它产生本地失败但整条路径都没有日志节点，则该分支不产生可连接的下游节点。
6. 若一个条件混合本地状态和多个调用结果，只连接经源码证明能够触发该日志分支的调用来源；本地原因不对应任何下游节点。
7. 对异步日志点，从消费者反向追溯其处理的数据对象、注册关系和生产者，只连接同一对象或等价状态的实际传播路径。
8. 如果异步错误设置了`SOCK_STAT_CLOSE`、队列关闭、资源耗尽等状态，只有后续 API 明确读取该状态并据此触发日志时，才能建立“后续 API 日志 -> 异步错误日志”的具体节点边。
9. 同一个异步日志可能由一个 API 产生数据、同时影响另一个 API。节点只定义一次，允许由多个根节点或具体日志节点复用。

在生成 JSON 前，先为每个物理日志点形成关系分析记录，至少包含：`文件:行号`、触发条件、来源分类（自身产生/下游透传/异步数据处理/失败被吞掉但日志可观测）、对应调用点、异步生产者和消费者、关联数据对象、传播变量或状态、直接下游日志点及代码证据。该记录用于自检，无需写入最终 JSON。

### 上游节点归属判定

1. 对每个物理日志点，沿实际控制流和失败传播路径向公共 API 反向追溯。
2. 如果途中存在能够捕获该失败并输出日志的节点，则由最近的上游日志节点连接当前节点。
3. 如果途中没有任何日志节点，则由对应公共 API 根节点直接连接当前节点。
4. 同一节点在不同路径上可能分别连接根节点和其他上游日志节点。
5. 函数调用关系只能用于定位候选路径，必须确认返回值、状态码或等价状态确实向上传播。
6. 所有纳入的具体故障节点必须至少能从 ubsocket_001~004 中一个根节点到达，禁止孤立节点。
7. 如果当前日志点产生失败，但其返回值被所有上游调用方明确忽略、覆盖或转换为成功，导致不存在故障传播到公共 API 的路径，则将其标记为“失败被吞掉但日志可观测”，对此类节点，不得连接到与其失败无控制或数据依赖的上游具体日志节点。为保证调用链日志覆盖和节点可达性，由能够执行到该日志点的公共 API 根节点直接连接。
8. 对异步日志点，先沿线程入口、事件回调或队列消费者反向追溯数据对象的生产者 API；如果异步错误被吞掉且没有后续具体日志，则由该生产者 API 根节点直接连接。
9. 如果异步错误通过状态影响后续 API，则由读取该状态并触发的最近具体日志节点连接异步错误节点；若后续 API 只返回 EOF、成功或无对应 ERROR 日志，则由该后续 API 根节点直接连接。
10. `Connect`或`Accept`创建、返回或持有某个 socket，不代表该 socket 后续所有异步错误都属于`Connect`或`Accept`。必须证明异步错误影响其当次返回、后续重试状态或明确检查的共享状态。
11. API 归属必须由日志点的实际执行入口、调用栈、数据生产者或状态读写关系证明，不得根据资源名称或方向推断。日志涉及`TX`、`RX`、发送队列、接收队列、TX/RX interrupt fd，只能说明被操作资源的方向，不能单独证明它属于`WriteV`或`ReadV`。
12. 对重试、回滚、解绑、刷新、销毁和析构路径，必须枚举日志所在函数的全部实际调用点，并分别反向追溯到公共 API。若函数由`Connect`或`Accept`的重试状态机同步调用，则其清理日志归属于对应的`Connect`或`Accept`路径；不得因为清理对象是 TX 资源而改挂到`WriteV`，也不得因为清理对象是 RX 资源而改挂到`ReadV`。
13. 只有能够从`WriteV`提交的具体 qbuf、请求上下文或状态写入追踪到日志点，或者日志点读取了由该 WriteV 路径写入的等价状态，才能归属于`WriteV`。`ReadV`同理，必须存在接收 qbuf、队列元素、CQE、用户上下文或状态传播证据。

归属判定时为每个候选根节点记录一条“归属证据”：`根 API -> 实际调用点/生产点 -> 传播对象或状态 -> 日志点`。无法写出完整证据链的根节点不得连接。反例：`UnbindAndFlushRemoteUmq`在 Connect/Accept 重试中获取 TX interrupt fd 失败，资源方向是 TX，但执行入口是连接重试清理，因此归属于 Connect/Accept，不属于 WriteV。

### 异步数据处理链

异步数据处理链是指公共 API 产生的数据或状态，在 API 调用栈结束后，由后台线程、事件循环、回调、定时任务或队列消费者继续处理的路径。确认异步链必须同时具备以下证据：

1. 公共 API 或其同步下游产生、提交或登记了具体对象，例如 qbuf、CQE、socket、fd、UMQ handle、队列元素、请求上下文或状态。
2. 异步入口处理的是同一个对象，或能通过 socket fd、UMQ handle、用户上下文、队列元素等字段建立明确关联。
3. 异步日志点位于该对象的实际处理路径中。
4. 若要把异步故障连接到后续 API 的具体日志，必须证明该故障写入的共享状态、socket 状态、队列状态或资源状态会被后续 API 检查并触发该日志。
5. 不得仅因为异步线程和公共 API 使用同一个全局单例、同一个类、同一个 socket 类型或同一个组件，就判定存在异步关系。

例如，`WriteV -> PostSend`提交 TX qbuf，底层据此产生 TX CQE，`TxCqePoller::RunInThread -> PollTx`处理同一 socket 和 qbuf 对应的 CQE，属于 WriteV 的异步数据处理链。若 CQE 错误回调设置`SOCK_STAT_CLOSE`，且后续 WriteV 检查该状态并记录错误，则后续 WriteV 日志可以连接到对应 CQE 错误节点。

### 日志静默控制变量

不得仅因`silent_poll_err`、`enable_log`、`verbose`、`debug_only`等人工日志控制变量在某个调用点为 false，就排除对应物理 ERROR 日志点。

1. 日志宏仍作为物理故障候选点提取。
2. 搜索控制变量的全部赋值点和调用方；只要同步或异步分析范围内存在能够满足日志条件的路径，就纳入该节点。
3. 控制变量仍属于日志触发条件和代码证据，故障原因中应说明必要的运行模式或控制条件。
4. 不得因为忽略控制变量而建立源码中不存在的具体节点因果边；例如两个日志位于同一轮询函数族中，但前一个日志并不检查后一个日志对应的失败结果时，二者不得连接。

## 操作步骤

### 步骤一：提取错误日志点

调用`find_ubsocket_log_err.py`，提取 UBSOCKET 源码中的`UBS_VLOG_ERR/UBS_SLOG_ERR`日志点。脚本输出的`file`字段是相对源码路径；生成故障模式的`文件名`时取该路径的最后一级裸文件名：

```bash
python3 .opencode/skills/failure-mode-generation-ubsocket/scripts/find_ubsocket_log_err.py <path-to-ubsocket-src>
```

### 步骤二：生成同步调用链候选

调用`generate_ubsocket_callchains.py`，提取四个公共 API 的候选函数调用链：

```bash
python3 .opencode/skills/failure-mode-generation-ubsocket/scripts/generate_ubsocket_callchains.py <path-to-ubsocket-csrc>
```

### 步骤三：确定分析范围

结合日志点和候选调用链，按照“顶层故障模式节点”“异步数据处理链”和“日志静默控制变量”规则，确定四个公共 API 同步及异步路径中需要分析的日志点。

### 步骤四：生成故障模式节点

按照“输出”中的字段规则、“故障聚合要求”和“故障模式结构”，分析并全局去重日志点，生成四个固定根节点和连续编号的具体故障节点，写入`./data/ubsocket/ubsocket_failure_mode.json`。

### 步骤五：生成故障关系

读取`/tmp/ubsocket_api_callchains.json`定位候选路径，按照“故障关系判定原则”“上游节点归属判定”和“异步数据处理链”规则逐个确定节点的直接下游关系，并在`./data/failure_mode_tree.json`中新增或覆盖`ubsocket`部分，保留其他组件内容。

### 步骤六：质量自检

按照“质量自检”逐项检查两个输出文件，修正遗漏、误收、重复、编号、字段格式、节点可达性和关系错误。

## 质量自检

1. 按照“顶层故障模式节点”和“异步数据处理链”规则，检查日志点是否完整且无误收。
2. 按照“输出”和“故障模式结构”规则，检查字段内容、编号及 JSON 格式，并确认每个节点均有不含目录的`文件名`字段。
3. 按照“故障聚合要求”，检查故障节点是否正确聚合和全局去重。
4. 检查`failure_mode_tree.json`的`ubsocket`部分是否覆盖全部故障编号、引用有效、无自引用，并确认所有具体故障节点均可从四个根节点到达。
5. 按照“故障关系判定原则”，逐边检查直接下游关系是否正确。
6. 按照“上游节点归属判定”“异步数据处理链”和“日志静默控制变量”规则，复核节点归属及特殊路径。
7. 确保从`Connect`、`Accept`、`ReadV`和`WriteV`出发的实际同步调用链中，所有错误日志宏调用点均已逐点分析，并由最终故障节点覆盖；按照“故障聚合要求”合并的多个日志点允许共用同一节点。静态调用图仅用于定位候选调用路径。
