# failure-mode-generation-umq

## 目标与输入

输入 UMQ 组件源码路径，基于公共 API 的同步调用和异步数据处理关系生成故障模式树。禁止参考项目旧产物、git 历史和`/tmp`临时文件；必须重新运行本 skill 的脚本并分析源码。

## 输出与节点格式

- 将全局唯一的节点定义写入`./data/umq/umq_failure_mode.json`。
- 将全部节点编号及直接下游关系同步写入`./data/failure_mode_tree.json`的`umq`部分，保留其他组件内容。
- 节点仅含以下字段：
  - **故障编号**：统一为`umq_xxx`。先按`/tmp/umq_api_callchains.json`的`roots`顺序，从`umq_001`起连续编号全部公共 API 根节点，再连续编号全局去重后的具体故障节点；禁止`umq_001_001`等分级编号。
  - **故障名称**：高度概括故障；推荐“xxx（操作）时yyy（原因概括）”，如“初始化xxx时参数无效”。不得直接出现函数名或日志原文，须结合函数作用和日志内容概括。
  - **故障现象**：给出识别日志所需的全部关键字。以`%d`、`%s`等格式占位符分割日志字面量，保留各段；格式为“依次匹配`关键字1`、`关键字2`”。无占位符时匹配完整字面量，如`Provider Bond register ops failed`。
  - **错误码**：具体节点按“错误码填写规则”填写；根节点为 JSON null。
  - **故障原因**：根据触发条件或下层调用语义总结直接原因，最好结合本函数作用并在故障名称上扩写；仍需向下匹配、无法定位根因时填“向下级匹配”。
  - **解决办法**：默认“无”。
  - **函数名**：仅填脚本输出的裸函数名，不得含类、结构体、命名空间或`::`。全限定名只保留最后一级（如`umq::Queue::Create`填`Create`）；根节点填`roots`中的 API 裸函数名。不得为区分同名函数重新添加限定符，应以文件、行号和日志内容区分。
  - **文件名**：源码裸文件名，根据`find_umq_log_err.py`脚本输出的`file`字段填写，不得携带目录路径。

### `文件名`要求

1. `文件名`只允许填写源码裸文件名。例如脚本输出的`file`为`transport/ub/umq_ub.c`时，最终 JSON 的`文件名`填写其最后一级`umq_ub.c`。
2. 具体故障节点填写物理日志点所在文件；聚合节点的多个物理日志点必须位于同一个裸文件名，否则不得用单个`文件名`掩盖歧义，应重新检查节点聚合是否合理。
3. 公共 API 根节点没有物理日志点，`文件名`填写该 API 在`umq_api.h`、`umq_dfx_api.h`或`umq_pro_api.h`中的声明文件裸名，并与`generate_umq_callchains.py`提取根节点时使用的头文件一致。

## 日志范围与聚合

1. 纳入公共 API 同步或已证实异步路径上的全部`UMQ_VLOG_ERR`、`UMQ_LIMIT_VLOG_ERR`，错误码不明确时仍须二次分析。
2. `find_umq_log_err.py`仅输出错误码明确且`needs_skill=false`的`UMQ_VLOG_WARN`；脚本输出且属于上述路径的 WARN 全部直接纳入，不再筛选或分析错误码。
3. 下文“所有日志点/故障点”均指脚本输出且属于上述路径的日志点。除根节点外，每个节点对应一个纳入的日志输出点。
4. 同一函数内日志内容完全相同（全字匹配）的多个物理日志点聚合为一个节点。
5. 在全部 API 的同步、异步路径间全局去重；同一日志故障只定义和编号一次，但可由多个根节点或具体节点指向。

## 节点与关系图

`umq_failure_mode.json`保存节点定义，`failure_mode_tree.json`保存有向的直接下游关系。具体节点不预分中间或叶子：value 非空的是中间节点，value 为`[]`的是叶子。共享节点和多层关系使其实际为有向图，而非固定层数的树。

边表示**故障因果传播**而非普通调用：`A: [B]`表示 B 的故障通过同步返回值、errno、状态码、异步数据对象或等价状态传播后触发 A 的日志。仅有函数调用事实不能建边。

公共 API 根节点没有物理日志点，是唯一可表达归属关系的节点。根边可以表示 API 失败路径的首个日志、API 所产数据的异步路径日志，或失败被吞掉但在该 API 功能路径中可观测的日志；不保证当次 API 返回失败。

### 公共 API 根节点

- 每个根节点对应`generate_umq_callchains.py`从`umq_api.h`、`umq_dfx_api.h`、`umq_pro_api.h`提取的一个 API，数量、顺序和编号以`roots`为准。
- 故障名称概括该 API 的功能失败；故障现象、故障原因和解决办法均填“向下级匹配”，错误码填 null，函数名填 API 裸函数名。
- 从这些 API 出发覆盖实际同步调用路径，以及由 API 提交的数据、缓冲区、请求或状态触发的后台线程、事件循环、回调、定时轮询和队列消费路径。既不在同步链中、又无法以具体数据对象或状态证明异步来源/影响关系的日志不纳入。
- 不得按函数名、业务用途或人为分类排除实际路径；初始化、重试、回滚、清理、刷新、解绑、销毁和析构等函数同样逐点分析。

### 具体故障节点

- 按本 skill 填写日志故障的各字段；是否为中间节点只由下游关系决定。
- 无纳入日志的同步/异步函数仅用于推导传播，不生成节点。仅在其确实继续返回下游失败或通过共享数据、缓冲池/队列等状态等价传播时，才跳过它连接最近上下游日志节点。
- 下游失败若被忽略、恢复或转为成功，且未留下后续 API 检查的等价状态，不得连接上游具体节点；满足“失败被吞掉但日志可观测”时，只由相关根节点归属。

## 故障关系判定

必须逐个物理日志点分析；同一函数的不同日志通常有不同触发条件和下游集合，禁止把函数调用图直接投影为故障图。

| 类型 | 条件与关系 |
| --- | --- |
| 一对多 | 日志检查子调用失败，而该返回可能源于多个具体故障；连接各失败路径上最近的下游节点。 |
| 一对零 | 日志由本地参数、状态、资源或操作触发，与下游失败无数据/控制依赖；value 为`[]`。 |
| 零对多 | 无日志中间函数继续返回子调用失败；跳过它，连接符合归属规则的上游日志与下游最近节点。 |
| 失败被吞掉但日志可观测 | 子函数记录日志，但调用方或异步执行者忽略/覆盖返回值或转为成功；不虚构上游具体节点边，由相关根节点直连，本节点仍按触发条件分析下游。 |
| 异步一对多 | API 所产数据在后台失败，并经同一对象/共享状态触发后续日志；后续日志连接异步失败路径上的最近节点。 |
| 异步零对多 | 无日志异步中间函数经同一对象/共享状态继续传播；跳过它连接最近异步故障节点。 |
| 异步可观测但被吞掉 | 后台记录失败，调度入口忽略返回且未改变后续 API 检查的状态；由数据来源 API 根节点直连。 |

逐点执行：

1. 读取日志函数和必要下游源码，定位`if/switch/catch/goto`、提前返回或失败清理路径；从条件反查定义和赋值，区分本地产生、具体调用返回/输出参数/errno/错误码及其转换。变量改名、布尔化、错误码映射和无日志包装不切断传播。
2. 仅当下游失败沿实际控制流到达日志时认定透传；调用存在、相邻或同函数均非证据。若条件混合本地状态和多个调用，只连接已证明能触发分支的调用来源，本地原因无下游节点。
3. 沿每个确认的失败路径向下，只连接最近具体日志节点；最近节点再连接更深层。无日志函数继续传播则穿透；整条本地失败路径无日志则无可连下游。
4. 枚举日志函数的全部物理调用点，包括直接调用、函数指针、结构体 ops、动态符号和回调；核实间接调用的实际绑定及传播，分别追溯公共 API/最近上游日志。有日志路径与无日志透传路径分别保留，不得找到一条有效路径即停止。
5. 即使分支最终返回`NULL`、`nullptr`、无效句柄或其他固定失败标志，也须反查条件中的`ret/res/status/errno`；最终返回只决定错误码写法，不能把下游故障误判成本地故障。同一下游状态的`if/else`、`switch`、队列类型等互斥日志分支须成组逐一分析。
6. 对异步日志，从消费者反查数据对象、注册关系和生产者，只连接同一对象或等价状态的真实传播路径。异步故障写入缓冲池、队列关闭、资源耗尽等状态后，仅当后续 API 明确读取并据此触发日志，才建立“后续 API 日志 -> 异步错误日志”边。
7. 同一异步日志可由一个 API 产生数据而影响另一个 API；节点只定义一次，可被多个根或具体节点复用。

生成 JSON 前，为每个物理日志点建立自检记录，无需写入最终 JSON。至少记录：`文件:行号`、触发条件、来源分类（自身产生/下游透传/异步数据处理/失败被吞掉但日志可观测）、对应调用点、异步生产者/消费者、关联对象、传播变量/状态、errno/状态、直接下游日志点及代码证据。另列全部物理调用点的调用类型、实际绑定、传播结论、最近上游或排除理由；将脚本未解析的间接调用与 ops 初始化、符号加载、回调注册交叉核对。

### 上游归属

1. 沿真实控制流和失败传播反查公共 API；若途中有捕获该失败并记录日志的节点，由最近者连接，否则由对应根节点直连。同一节点在不同路径可分别连接根节点和上游日志。
2. 调用图仅定位候选路径；必须证明返回值、errno、状态码或等价状态确实传播。所有具体节点必须从至少一个 UMQ 根节点可达，禁止孤立节点。
3. 若日志失败被所有上游明确忽略、覆盖或转成功，标记“失败被吞掉但日志可观测”；不得连接无控制/数据依赖的上游具体日志，由能执行到它的 API 根节点直连。
4. 异步日志先沿线程入口、事件回调或队列消费者反查数据生产者 API：错误被吞且无后续具体日志时，由生产者根节点直连；错误经状态影响后续 API 时，由读取状态并触发的最近日志连接。若后续 API 仅返回成功或无对应 ERROR 日志，则由该后续 API 根节点直连。
5. API 创建、返回或持有资源，不表示该资源全部异步错误均归属它；须证明错误影响当次返回、后续重试状态或明确读取的共享状态。归属须由实际入口、调用栈、数据生产者或状态读写证明，禁止按资源名或方向推断。
6. 对重试、回滚、解绑、刷新、销毁和析构路径，枚举全部实际调用点并分别反查 API。每个候选根均须记录完整证据链：`根 API -> 实际调用点/生产点 -> 传播对象或状态 -> 日志点`；证据不完整不得连接。
7. 对每条跨组件边，确认 UMQ 源节点可从所有能触发该外部调用的 API 到达；否则按内部断链回查间接调用、无日志透传和遗漏调用点。

### 异步数据处理链

异步链指 API 所产数据或状态在调用栈结束后，由后台线程、事件循环、回调、定时任务或队列消费者继续处理。必须同时证明：

1. API 或同步下游产生、提交或登记具体对象，如 qbuf、缓冲区、UMQ handle、队列元素、请求上下文或状态；
2. 异步入口处理同一对象，或可由 handle、用户上下文、队列元素字段等明确关联；
3. 日志位于该对象的实际处理路径；
4. 若连接后续 API 的具体日志，异步故障写入的共享/缓冲池/队列/资源状态确被该 API 读取并触发日志。

仅共用全局单例、类或组件不能证明异步关系。例如：`umq_buf_alloc -> fetch_from_global -> async_expand_global_pool`通过`pthread_create`提交任务，回调处理同一扩容池，故属于该 API 的异步链；但提交函数返回 void，独立线程回调的返回被忽略，二者的 ERROR 日志分别属于“失败被吞掉但日志可观测”和“异步可观测但被吞掉”，均由`umq_buf_alloc`根节点直连。

## 错误码填写规则

先运行`scripts/find_umq_log_err.py <UMQ源码路径>`并读取`/tmp/umq_log_err.json`。用顶层`error_definitions`查十进制值，用每条日志的`log_macro`、`error_code`、`error_source`、`error_expression`、`needs_skill`确定输出。

`错误码`仅允许错误码 string、裸整数或 JSON null，例如`"UMQ_ERR_EINVAL(22)"`、`0`、`null`。`UMQ_FAIL`和`UMQ_INVALID_*`也是可输出符号。宏值直接取`error_definitions`；即使源码`return -UMQ_ERR_EINVAL`也输出`UMQ_ERR_EINVAL(22)`而非负值。裸`0/-1`输出 JSON number，不加引号。一条日志能确定多个具体错误码时，结合日志语义选择最合适者。

按顺序处理：

0. `log_macro=UMQ_VLOG_WARN`：直接纳入并使用脚本已明确的`error_code`；WARN 不会要求二次分析。
1. `error_code`为 string：从`error_definitions`查值并输出`宏(value)`；允许`UMQ_ERR_*`、`UMQ_FAIL`、`UMQ_INVALID_HANDLE`、`UMQ_INVALID_FD`，不得按日志文字改写脚本结论。
2. `error_code`为整数`0/-1`：原样输出 number，不查定义、不加宏名。
3. `error_code=null, needs_skill=false`：输出 null，表示脚本已确认无法对应宏或无错误传播，不再猜测。
4. `error_code=null, needs_skill=true`：按下述规则分析；仅在证明可输出宏或裸`0/-1`时填写，否则为 null。

`error_source`仅定位传播渠道：`return`沿返回表达式、分支赋值和 goto 清理分析；`errno`沿 errno 赋值分析，此时函数返回的`NULL/0/UMQ_FAIL`仅表失败，具体错误优先取 errno；`none`直接为 null；`unknown`检查日志分支，无法证明则为 null。`error_expression`只是分析入口，禁止将`ret/res/status/NULL`等原样输出。

仅对`needs_skill=true`二次分析：

1. 从日志分支找到实际`return`、errno 赋值或 goto 清理出口；若返回变量，沿当前失败分支反查最近赋值，跨 goto 检查清理标签和最终覆盖。
2. 变量来自下层调用时，只收集当前失败条件可达且能明确归一为`UMQ_ERR_*`、`UMQ_FAIL`、`UMQ_INVALID_*`的返回；遇`*_convert()`等转换函数则检查每个可达分支。
3. 显式标准 errno 符号（如`EINVAL/-EINVAL`）可按`error_definitions`映射；不得因任意外部 enum 或整数恰好同值而映射。
4. 最终表达式为裸`0/-1`时输出 number。同一路径有多个已确认可输出宏时全部输出并去重；若另含未知动态错误，只输出已证明的宏，不推测动态部分。

以下情况必须为 null：返回`NULL/nullptr`等空指针；void 函数记录日志后返回，或之后`continue/break`；只能确定运行时`ret/res/status/errno`而不能静态定值；返回无明确 UMQ 转换的下层私有码、URMA status 或外部 enum；只能根据日志文案或 if 条件猜测。禁止由“invalid parameter”“alloc failed”等文案猜`UMQ_ERR_EINVAL/ENOMEM`，也禁止输出`NULL(0)`、`nullptr(0)`或原始变量名。

## 操作步骤

1. 运行`python3 .opencode/skills/failure-mode-generation-umq/scripts/find_umq_log_err.py <path-to-umq-src>`提取日志点。脚本输出的`file`字段是相对源码路径；生成故障模式的`文件名`时取该路径最后一级裸文件名。
2. 运行`python3 .opencode/skills/failure-mode-generation-umq/scripts/generate_umq_callchains.py <path-to-umq-src>`生成候选调用链。读取`/tmp/umq_api_callchains.json`：以`roots`确定根和编号，以`functions/edges`定位候选路径；检查`analysis/unresolved_indirect_calls`并结合源码补全间接调用。候选调用关系必须按故障传播规则复核。
3. 按“公共 API 根节点”和“异步数据处理链”确定同步、异步分析范围。
4. 按错误码规则处理脚本结论，并对`needs_skill=true`项分析源码。
5. 按日志范围、节点格式、聚合及图结构生成`./data/umq/umq_failure_mode.json`。
6. 逐点确定直接下游关系，在`./data/failure_mode_tree.json`中新增或覆盖`umq`，保留其他组件。
7. 完成下列质量自检并修正问题。

## 质量自检

1. 日志无遗漏、误收；`unresolved_indirect_calls`候选路径已复核。
2. 节点字段、命名、裸函数名、裸文件名、连续编号和错误码均符合规则；每个节点均有不含目录的`文件名`字段；同步/异步路径已全局去重。
3. 逐边复核控制流、最近下游和上游归属；异步归属/传播证据完整，被吞掉的同步/异步日志由正确根节点直连。
