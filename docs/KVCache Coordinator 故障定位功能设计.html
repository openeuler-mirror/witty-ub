KVCache Coordinator 故障定位功能设计

适用范围：灵衢 KVCache 部署中由中心管理节点（coordinator pod）承担的管控面功能。本指南整理 coordinator 主要业务流、各业务流故障时的终态入口关键字（可直接用于正则匹配），以及故障上下文的获取与相关性确认方法。

日志真实格式取自演练场景 1022/coordinator/zzz-coodinator-0/（2026-10-14 数据），源码位置对应 yuanrong-datasystem/src/datasystem/。

0. 功能设计总览

目标：在 witty-ub 现有通断故障监控与 get/set 请求监控基础上，平行新增 coordinator 故障定界能力——对中心管理节点日志做解析、关联、计数与时序分析，并为 agent 模块提供 skill/wiki/案例支撑。

4. 故障上下文获取方法

4.1 本节点（coordinator pod）展开

  • 确定入口（最终故障结果）：用 §3 的终态正则扫 kvcache_coordinator.INFO.log，命中行即最终故障结果（如 outcome=finalized、FORCED_READY、NOTIFY_FAILED），记其时间 T。
  • 取时间窗（只取故障前）：[T-60s, T]——只取入口事件本身 + 其之前的日志，用于还原"导致该最终结果的前置链路"。故障后的日志不属于本流程（如需验证处置闭环/连锁影响，再另行向后扩展）。
  • 串事件链：在 [T-60s, T] 窗口内过滤 CLUSTER_*/COORDINATOR_*，按时间排序，用 §2 的事件链还原从缺失观察到定案的前置过程（这些事件全部发生在入口之前，如 missing_first_observed → WITNESS_PROBE_ROUND_STARTED → REPORT_RECEIVED → FAILURE_ALLOWED → finalized）。
  • 量化验证：kv_metrics.log 按 cycle 对齐 [T-60s, T] 窗口，比对 delta 字段是否同步跳变：
  • brpc_rpc_e2e_fail_latency delta>0 或 coordinator_watch_rpc_failure_total delta>0 → 故障窗口确认在 coordinator 侧；
  • 三份指标均无跳变而业务仍失败 → 问题在下游/网络，coordinator 仅是目击者。
  • 排除进程底色：kvcache_coordinator_operation.log 中确认 T 之前无新的 OPERATION_START（进程未重启），CONFIG_INIT 中的 node_dead_timeout_s/enable_ub_fault_isolation 与故障表现匹配。

4.2 跨节点佐证（仅取故障前/入口时刻）

在"只关注故障前"的视角下，worker 节点日志用于佐证故障前的事实，帮助排除"该节点本就异常"的干扰：

核对环节日志关键字（时间 < T 或入口时刻）佐证内容
故障前已注册coordinator 侧 CLUSTER_KV_CHANGE event_type=0 key=.../cluster/<addr>故障节点在 T 之前已正常注册为成员
故障前数据面存活worker 侧 kvcache.INFO.log 的 Register client / object_posix故障前该节点数据面正常服务
探活裁决证据CLUSTER_WORKER_PROBE ... action=WITNESS_PROBE_REPORT_RECEIVED ... result=UNREACHABLE/REACHABLE（入口时刻）定案依赖的探活事实
注：故障后的处置结果（如 rejoin、SCALE_OUT、拓扑 published）不属于本流程范围，不再核对。

5. 上下文相关性确认线索（判断事件属于同一故障）

核心：只把共享同一"关联键"的事件视为同一故障的上下文；关联键不同的事件属于其他业务过程，必须排除。

5.2 各业务流专属主键（关联逻辑因业务流而异）

通用主键覆盖所有流，但每个业务流还有自己的专属主键——串链时必须先判断事件属于哪个业务流，再选用对应主键。这些主键均为单调递增/唯一，同值必属同一业务过程。
业务流专属主键递增规则生命周期关联链示例
B1 选主/bootstrapRaft term + index、group_id选举次数 term+1；日志 index+1稀疏（换届才变）LEADER_ELECTED term=N ↔ LEADER_STOPPED term=N ↔ Raft 回调事件 term=N index=...
B2 拓扑恢复version + store_revisionversion 落版+1；store_revision 每 KV 写+1恢复期（秒~分钟）RECOVERY_CANDIDATE version=17 → READY version=17 → READY_STORED_AUTHORITY store_revision=44
B3 成员/保活成员 key + KV revision同一节点 key 的 revision 单调递增常驻CLUSTER_KV_CHANGE key=.../cluster/<addr> revision=9 → 同 key 后续 put/delete 用 revision 续链
B4 watchwatchId + revisionwatch 注册时 id+1；rewatch 从某 revision 续通道生命周期NOTIFY_FAILED watchId=10 ↔ BACKPRESSURE_OVERFLOW watchId=10 ↔ CANCEL_FAILED watchId=10
B5 故障检测probe_id（尾号递增）每探活轮 +1短命（秒级，CLEARED 后失效）ROUND_STARTED probe_id=...298 → REPORT_RECEIVED → FAILURE_ALLOWED 同 298
B6 变更下发batch_epoch（内嵌任务 key）每变更批 +1中寿（30s~180s）CHANGE_BATCH batch_epoch=18 ↔ tasks/delete/d-e18-... ↔ finalized committed_version=19
B7 生命周期coordinator_id + state 迁移无序号，靠状态机进程全程state=started → running → stopping(reason) → stopped

主键生命周期对比（决定"某 id 是否仍有效"）：probe_id 秒级、一轮 ROUND_CLEARED 即失效；batch_epoch 30s~180s 跨批；version 长命、贯穿多个批；term 极稀疏。关联方向也不同：探活链是单向轮次（298 结束才能开 299）；变更批是开闭区间（start→finalized）；版本是全局顺序（只增）；成员保活是按 key 回溯。

5.3 跨业务流交接键

业务流之间的衔接只认 version（唯一贯穿多个流的键）：

B5 探活链（probe_id=298）→ FAILURE_ALLOWED
   ↓ 交接：outcome=finalized committed_version=19          （B5 结束）
B6 变更批（batch_epoch=18）→ RING cas_committed version=19 → CHANGE_BATCH finalized committed_version=19   （B6 闭环）
   ↓ 交接：RING version=19 ↔ worker 侧 published version=19
B2 恢复/回归（version 续到 20、21）→ 新节点 rejoin（id_prefix 变化）→ 新探活轮（probe_id=299）

注意：probe_id/batch_epoch/watchId 不跨流，跨流时只有 version 可交接；跨节点时只有 version + cluster + 时间戳可对齐。

5.4 同一故障的确认规则

  • 同 cluster：所有上下文事件必须与入口事件的 cluster 一致，不同 cluster 的事件一律排除。
  • 同 probe_id：WITNESS_PROBE_ROUND_STARTED → WITNESS_PROBE_REPORT_RECEIVED → WITNESS_PROBE_FAILURE_ALLOWED 必须共享同一 probe_id；出现新的 probe_id 表示开启新探活轮（前一轮 ROUND_CLEARED），不代表当前故障。
  • 版本闭环：CLUSTER_FAILURE ... outcome=finalized committed_version=N 之后，必须能找到 CLUSTER_RING ... status=cas_committed version=N 与 CLUSTER_CHANGE_BATCH ... action=finalized ... committed_version=N。缺任一环 = 变更未真正落地，即为"决策对、执行漏"的嫌疑点。
  • 同 target：故障对象地址一致（注意新节点 rejoin 后 id_prefix 会变，见实例 192.168.235.129:31501 从 ff84ffb3-a69 变为 2e1785d2-c0c，属同一节点重新入环）。
  • 时间连续性：同一故障的事件时间单调递增且间隔在流程阈值内（missing→finalized < node_dead_timeout_s 数量级；变更批 window_ms=30000/180000）。

5.5 排除规则（判断事件不属于当前故障）

情况判定
cluster 不同完全无关，排除
probe_id 不同且前一轮已 WITNESS_PROBE_ROUND_CLEARED上一轮探活已结束，新一轮嫌疑是独立事件
coordinator_id 不同跨 coordinator 换届，需按代际重查上下文
同一节点 state=ACTIVE 的 CLUSTER_RING（如 version=17 正常环）与含 state=FAILED 的环（version=18）并存前者是变更前快照，后者才是本故障产物；用 version 递增确认时间先后
worker 侧 CLUSTER_RING status=published 的 version 与 coordinator 侧 committed_version 不一致worker 尚未应用该版本，属"执行滞后/丢失"，需查 CLUSTER_WATCH_NOTIFY_FAILED
trace_id 相同的连续事件同一线程内同一流程，属强相关上下文

5.6 通用关联路径（4 步法）

识别出某业务流故障后，用该流的专属主键关联即可，但入口事件行可能不带全部主键（如 outcome=finalized 有 batch_epoch 但无 probe_id），需用中转键回捞补全。
① 解析入口行   → 提取所有键字段（batch_epoch / probe_id / watchId / version / target / coordinator_id）
② 同流直连     → 用专属主键 grep，捞该业务流全部事件
③ 中转补全     → 若入口行缺某主键，用 version / target / 成员 key 中转回捞，再提取缺失主键继续
④ 闭环校验     → version 三处一致（FAILURE / RING / CHANGE_BATCH）→ cont-trace_id 合并线程
              → 跨节点用 version + cluster + 时间戳对齐

实例：从 CLUSTER_FAILURE ... outcome=finalized batch_epoch=18 ... committed_version=19 入口出发

步动作grep 依据捞到什么
1同流直连batch_epoch=18CHANGE_BATCH 的 start/deadline_set/finalized 三事件 + 任务 key d-e18-... + notify 下发
2版本闭环version=19 / committed_version=19CLUSTER_RING status=cas_committed version=19（三处闭环确认落版）
3回溯探活链target=192.168.235.129:31501 或 version=17捞回 missing_first_observed / WITNESS_PROBE_ROUND_STARTED / REPORT_RECEIVED / FAILURE_ALLOWED
4提取探活主键第 3 步结果中的 probe_id=...298用 298 再 grep → 确认整条探活链次序完整
5线程合并各行的 cont-xxx同一控制循环毫秒级连续事件合并成链
6跨节点佐证（可选）cluster= + 时间戳（< T）worker 侧故障前事实（注册/数据面存活），不做故障后闭环核对

要点：

  • 专属主键能隔离并行过程——同时刻其他业务流（其他节点注册、另一批 SCALE_OUT）用主键过滤后自然排除，优于时间过滤；
  • 不能只用单键——完整上下文 = probe_id（探活）+ batch_epoch（变更批）+ key+revision（KV 序列）+ cont-trace_id（线程）各层键的并集；
  • 跨流必走 version——B5→B6、B6→B2 的交接点都是 version。
