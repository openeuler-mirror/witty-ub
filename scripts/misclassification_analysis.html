核心原因
  • 真实标签与预测标签属于同一故障家族，特征模式高度相似。
  • ubm_failure 与 ubse_failure 在时延分布、segment_ranking上几乎不可区分——两者都导致GET操作超时，区别仅在UB返回的具体错误码(UBM vs UBSE)。
  • local_ub 变体(all_port_down / all_port_lanedown / two_port_flashdown)的时延特征几乎完全重叠，因为都表现为"所有端口不可用"的宏观效果。
  • worker_process_remote_local_ub 的 single_port_down 与 link_loss 在failure_mode_dist上高度重叠，都产生相似的runtime错误码分布。
  • scale_in_remote_ub 的 nfe 与 link_down 在缩容场景下故障传播路径一致，导致特征收敛。
失效特征
  • failure_mode_dist：UBM和UBSE故障产生的runtime错误码集合高度重叠。
  • segment_ranking：同一故障族内的时延段排序模式一致。
  • affected_operation_dist：受影响操作分布无差异。
潜在区分特征(未使用)
  • UB错误码的具体类型(UBM vs UBSE)——当前feature提取未区分。
  • 端口故障的物理拓扑差异(全部端口 vs 单socket双端口 vs 闪烁断开)——需要拓扑感知特征。
  • 故障注入的精确方式(链路丢失 vs 端口down vs lane down)——运行时可能产生微妙的日志差异。

算法改进
  • 近亲惩罚机制：当Top-1和Top-2属于同一故障族且置信度差<0.01时，触发"近亲消歧"子流程，使用更细粒度的特征(如ub_error_type)做二次匹配。
  • 族内排序规则：同一族内如有多个候选，按failure_mode_dist的Jaccard差异做二次排序。
近亲处理
  • 可选：合并UBM/UBSE：如果业务上两种故障的恢复策略相同，可合并为client_get_ub_failure一个类型，减少不必要的区分。

核心原因
  • 真实标签与预测标签属于不同故障族，但同属一个品类(latency/mixed)，时延特征模式存在交叉。
  • local_ub ↔ remote_ub 互混(4例)：本地UB和远端UB的端口故障在时延段排序、p99/p50比率上高度相似——都是"远端RPC超时"的表现。

失效特征
  • segment_ranking：local_ub和remote_ub的时延段排序几乎一致(都是remote_worker_rpc最大)。
  • pod_concentration / affected_pods_count：本地vs远端故障在pod分布上可能有差异，但当前权重不足。
  • failure_mode_dist：worker_process族的错误码分布交叉严重，缺少"族标识性错误码"。
潜在区分特征(未使用)
  • 故障作用域(scope)：local_ub仅影响本节点，remote_ub影响跨节点——可从pod分布和网络拓扑推断。

  • UB实例标识：从日志中提取UB实例名，区分local_ub和remote_ub。
  • worker进程角色：区分remote worker和local worker的错误来源。

💡 改进建议

特征改进
  • 新增 fault_scope 特征：标注故障作用域(local_node / cross_node / cluster_wide)。
  • 新增 rpc_direction 特征：标注RPC超时方向(outbound_local / outbound_remote / inbound)。
  • 增强 pod_concentration 权重：local_ub应表现为single_pod或few_pods，remote_ub应涉及多个pod。
  • 新增 ub_instance_type 特征：从日志中提取UB实例的local/remote属性。
算法改进
  • 族门控规则：如果failure_mode_dist包含local_ub特有错误码(如runtime_1036/runtime_1051)，优先匹配local_ub族。
  • 作用域门控：如果affected_pods_count=1且pod_concentration=single_pod，排除remote_ub族候选。
  • 调整segment_ranking权重：对local_ub vs remote_ub的区分度不足，需降低segment_ranking在该场景下的权重。
数据改进
  • 为local_ub_all_port_down、remote_ub_single_port_down等类型增加更多训练样本(当前仅1-2个)。
  • 确保训练集覆盖local_ub和remote_ub的对称场景，避免样本数偏差导致匹配偏向。
● 特征饥饿 19 例 [收起]

🔬 根因分析

核心原因
  • 训练集仅有1个样本，导致该故障类型的特征模板极不稳定，匹配时容易漂移到样本更丰富的类型。
  • 1样本训练集无法捕捉故障的时延分布方差，导致test样本的时延特征与训练样本的自然偏差被放大。
  • dfx_worker_set_exit(17样本)和dfx_write_remote_tcp_dalay(3样本)作为"样本富集"类型，成为天然吸引子，吸收了大量特征饥饿的案例。
  • 19个特征饥饿案例中，14个被吸引到高样本类型(worker_set_exit/write_remote_tcp_dalay/local_ub_single_port_down)。
失效特征
  • 所有特征在1样本训练集上均失效——无法建立合理的特征分布模型。
  • confidence分数虚高(最高0.9385)：因为训练样本少，特征模板"刚好"与测试样本在某些维度匹配，但这是过拟合，不是真正的相似。
潜在区分特征(未使用)
  • 故障注入元信息：故障类型名称本身包含丰富语义(如etcd_cluster_fail暗示etcd相关)，可用于规则辅助。
  • 时序特征：故障发生前后的时序变化模式(如etcd故障通常先有etcd日志异常)。
  • 上下文特征：故障发生时的系统状态(如etcd是否可达、UB是否已初始化)。

■ 特征贫乏吸引子 3 例 [收起]

🔬 根因分析

核心原因
  • dfx_write_remote_tcp_dalay的特征模板过于宽泛：其3个训练样本的时延特征覆盖了"远端写超时"的整个光谱，导致多种不同故障(ubse_fault/two_port_flashdown)都被吸引。
  • dfx_worker_set_exit作为17样本的"超级类型"，其特征模板是多种exit场景的平均，丢失了细节特征，成为通用吸引子。
  • 这两种类型的failure_mode_dist为空(仅时延特征)，意味着它们缺乏"排他性"特征来拒绝不相关的匹配。
失效特征
  • failure_mode_dist为空：write_remote_tcp_dalay和worker_set_exit都不产生独特的runtime错误码，无法通过错误码排除不相关候选。
  • segment_ranking过于通用：两者都表现为"全链路超时"，无法区分具体故障位置。
潜在区分特征(未使用)
  • 写操作特征：write_remote_tcp_dalay应只在写操作(DS_POSIX_SET)上超时，而ubse_fault/mixed类型应在GET操作上也有表现。
  • 进程退出特征：worker_set_exit应有worker进程退出日志，其他类型不应有。
  • 故障持续时间特征：不同故障的持续时间分布不同，可作为区分。

🔬 根因分析

核心原因
  • 真实标签与预测标签属于不同品类(latency vs connectivity vs mixed)，品类门控未能有效拦截。
  • 当前匹配算法缺少品类级别的硬门控，导致latency类型可以被误匹配到connectivity类型。
失效特征
  • fault_category特征未被用作匹配的门控条件，仅作为后置标签。
潜在区分特征(未使用)
  • fault_category本身——应作为硬门控使用。

本次分析中未发现跨品类混淆案例——所有误分类案例的真实类型与预测类型均属于同一品类。

💡 改进建议

算法改进
  • 品类硬门控：在匹配前，先用fault_category过滤候选集，仅保留与测试案例同品类的类型。
  • 品类软门控：对跨品类匹配的置信度施加惩罚因子(如×0.5)。
