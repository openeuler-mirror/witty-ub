# 默认标签策略：新增数值特征分类器＋全特征余弦 K4 退化

普通诊断统一调用 `scripts/default_matching.py`，策略标识为
`numeric-units-classifier-cosine-fallback-v1`。无需指定模型或实验目录。

## 正常报告生成

```bash
python3 ../diagnostic-report-generation/scripts/generate_report.py \
  /path/draft.json /path/report.html --log-dir /path/raw_logs
```

此命令实际提取日志观测，计算新增数值分类器和全特征余弦 K4，并渲染报告。
标签退化投票默认使用当前发布的参考库，无发布版本时使用内置资源。
`--cases` 提供候选信封。`--api-base` 显式使用案例库中已验证的候选进行标签退化投票。
部署中配置 `WITTY_API_BASE` 时，报告自动跨库读取已确认案例用于展示。
`--labels-only` 导出同一路径生成的标签 JSON；`--classifier-model` 仅用于显式覆盖。

初始资源在本 skill 的 `assets/default_label_policy/`，后台重训后优先读取共享目录的已发布版本：

| 文件 | 作用 |
| --- | --- |
| `numeric_classifier.json.gz` | 全部 474 份开发报告拟合的部署模型，Logistic C=1，标准库推理 |
| `cosine_bank.json.gz` | 474 个来源、514 个故障候选的全特征观测及参考标签 |
| `manifest.json` | 文件校验、特征版本、训练来源与用途说明 |

运行时不读取 `/home/witty-ub-logs`、仓库根 `scripts/`、GT 或 sklearn，
也不使用 v6 的 474 套逐折权重；那些权重仅是历史评估记录。
部署模型是一次全量拟合，不代表有新的独立测试成绩；79.96% 是 v6 的逐折重训数值分类器成绩。
普通诊断不会训练或更新权重；后台重训与诊断请求分开执行。报告中记录 `model_id` 和真实采用的路径。

## 特征和退化条件

`mined_log_features_v2.scan` 从真实 I/W/E 消息列提取角色/组件/阶段上下文。
主模型只使用 `numeric_units`：统一单位耗时/大小、样本数、均值/极值、对数分布和近似分位桶。
它不叠加基线、词语、模板或事件组合。标签、报告结论、根因文字、文件夹场景名不进入特征。
保持 v6 同版单位规则：显式 ns/us/ms/s 等单位会转换，裸字段仅推断 us/ms 后缀；
其他未识别单位的裸值保留为 `value`，不假定为微秒。扩展单位规则须升级提取器并重建部署资源。

每次同时计算 `all_context_v2` 的余弦 K4，作为历史案例参照和退化结果：
基线观测＋新增数值＋阶段/显式状态＋成功失败对比＋相对时间窗＋上下文词语、模板和组合。
仅从过滤后的参考来源确定词表和 MaxAbs 缩放，不使用分类器系数；K=4、margin=0.05。
同来源、别名和完整日志内容相同的参考来源在投票前排除，身份只用于排除，不成为匹配键。

以下情况选择余弦 K4，并记录 `fallback_reason`：

- 没有可用数值观测，或数值键全部不在冻结模型词表内。
- 默认分类器文件缺失、损坏或版本不兼容。
- 多故障报告需要逐故障归属，缺少独立故障日志时使用下述多故障规则。

没有可比观测或参考候选时保持空标签，不把缺失解释为健康，也不按类别先验强行输出标签。
明确的误操作故障码规则仍优先。模型分数未做置信度校准，不能直接作为根因正确概率。
API 新候选若没有完整观测，按已知部分比较，不从标签或根因文字补造数值、模板或日志。

## 单故障与多故障

报告级结果写入顶层 `label_matching`。其 `decision` 是实际采用的标签，
`retrieval_decision` 为余弦 K4 参照；`feature_usage`、模型 ID、观测哈希和退化原因可追溯。

- 单故障：采用报告级主预测；主模型不可用时采用余弦 K4。同步更新该故障的一级标签。
- 多故障：报告级分类器照常运行并展示总体预测；不把同一总体预测复制给所有故障。
  每个故障以自身结构化观测＋共享报告日志计算全特征余弦 K4，记录
  `multiple_faults_require_fault_scoped_evidence` 和实际观测作用域。
  这是当前的逐故障退化口径，不宣称已有 79.96% 的逐故障归属准确率。

一级标签改变时舍弃草稿二级标签。二级标签可通过下述案例证据补全，细粒度根因仍需现场证据。
模板展示报告级标签预测及数值分类/余弦退化来源，原渲染器校验结论标签与策略输出一致。
报告级预测在页头展示，各故障的一级/二级标签仍在各故障档案中。
分类器与同作用域的 K4 结果不一致时记录 `disagreement=true` 并在页头提示；
分类器仍按主路径采用，不因不一致本身触发退化，不比较未经校准的模型分数与余弦分数。
多故障的总体预测与某条故障标签不同属于作用域差异，不能据此将所有故障改成同一类。

## 报告中的历史案例

每条故障完成标签判定后，从当前已确认案例中选取一级标签相同的候选，
使用共享的 `all_context_v2` 观测空间计算余弦相似度，并排除当前报告、日志来源相同和缺少实质共有观测的案例。
优先复用已发布的观测向量。旧案例可用已保存的错误码、故障模式、阶段桶统计和日志语义轮廓生成向量。
每条故障最多展示三个案例，保留案例自身的两级标签。一级标签为空或没有同类可比案例时，历史案例列表为空。

`knowledge_candidates` 提供报告可引用的排序结果，`candidates` 和 `retrieval_decision` 记录共用策略的候选与 K4 投票。
三者均写入匹配旁车 JSON。案例的根因和处置内容用于展示，现场故障结论依据本次取证。

二级标签补全复用同一级的案例候选，要求故障自身的证据锚点与案例特征共享同一个
`failure_mode_id`。至少两个不同来源的已确认案例须支持同一个有效二级标签，候选标签冲突时保留空值。
有效草稿二级标签优先，明确的案例建议随报告保存在 `label_matching.second_level_decision.case_suggestion`。

## 观测导出和调用

```bash
python3 scripts/match_baseline.py --report /path/report.json \
  --log-dir /path/raw_logs --out /tmp/query.json
python3 scripts/match_baseline.py --query /tmp/query.json \
  --cases /path/cases.json --out /tmp/matches.json
```

导出 `.structured.json`、`.raw.json`、`.mined.json`，本地/HTTP 匹配自动读取旁车。
`match_cases.py` 通过同一 `default_matching.match` 作最终标签决策。
旧的 `fixed_matching.py`、[固定 K4 说明](FIXED_FEATURE_MATCHING.md)保留给历史对照，
不作为普通报告的默认决策。

## 已确认案例变更后的自动训练

后端 `latency.services.fault_classifier` 每 5 秒检查一次有效已确认案例集合。
确认新增、归档/删除、源报告级联删除以及分类/检验状态变化均可触发；重启后会与持久化指纹核对。
案例库两版前端顶部展示待训练、训练中、完成、失败或数据不足状态。
训练期间每秒检查变更；再次变化时终止旧训练子进程，清理未发布产物，立即用最新集合重启。
高频连续操作可能连续重启，以最终稳定的数据集合为准；旧任务不能覆盖最新结果。

训练数据包含初始 474 个核验来源，以及当前符合条件的已确认来源。
初始来源与案例按 `kb_id` / 来源名关联后由案例库接管：当前标签覆盖原标签，删除后不再从初始资源复活。
未被案例库接管的历史核验来源仍保留，因此案例条数不等于训练样本数，删除少量案例也未必低于训练门槛。
接管身份作为删除记录持久保存；不能只删除模型目录来实现案例删除。

进入训练的新增来源必须同时满足：

- 案例处于有效 `confirmed` 状态，且 `verification_json.closed_loop=true`，一级标签在五类范围内。
- 源报告仍已确认，快照哈希、故障 ID 和标签与案例一致；多故障报告的相关故障已全部确认。
- 有可读取的真实日志，或经过哈希验证的同版数值观测旁车；内置来源也可在身份和原始观测指纹完全匹配时复用历史观测。

不从根因、结论或真实标签生成输入特征。缺少检验或观测的案例跳过并在状态中计数。
同日志内容的别名合并为一个独立来源；同一报告的多个标签共享总权重 1，不以故障条数重复放大样本。
主模型仍是 `numeric_units`、Logistic C=1、无类别重加权，每次从有效全量样本重新拟合。
报告生成前的预测与事后确认标签仅作追溯记录；自动训练不生成新的独立测试准确率。

### 数据不足的处理

当前保护门槛：至少 20 个独立来源、至少两类有效标签、每个已出现类别至少 5 个独立来源。
按去重后的来源计数，多标签来源分别计入其覆盖类别。门槛用于避免明显不适合训练的数据集，不保证准确率。
低于门槛时不拟合、不沿用包含已删除来源的旧分类器，而是原子发布仅含当前有效来源的 K4 参考库。
状态为 `insufficient_data`，显示数量与具体不足原因；主推理记录 `insufficient_training_data`，自动退化到全特征余弦 K4。
参考库也为空或没有可比观测时，保留空标签，明确的用户使用故障码规则仍保留。
补充符合条件的案例后自动重新判断门槛并训练；不足状态不会循环重试同一集合。

### 发布、失败与部署

模型与参考库写入不可变版本目录，校验通过且案例指纹仍一致后原子切换 `active.json`。
单次匹配固定同一版本的模型和参考库；版本路径用于缓存，后续匹配自动读取新版本。
普通训练异常保留上一发布版本，界面提示失败，支持操作人手动重试；同一失败集合不无限重试。
“数据不足”属于明确退化状态，与训练异常区分。训练期间生成报告仍使用上一发布版本，因此界面建议等待完成。

共享目录优先用绝对路径环境变量 `WITTY_CLASSIFIER_MODEL_DIR`，否则优先为 `${WITTY_DIR}/fault_classifier`；未设置 `WITTY_DIR` 时才兼容回落到 `WITTY_REPORT_DIR` 的同级
`fault_classifier/`（默认 `/var/witty-ub/fault_classifier`）。各部署启动器均显式导出模型目录，后端和 Agent 必须看到同一目录；
源码与 RPM 默认同为 `/var/witty-ub/fault_classifier`；RPM/容器后端独立从
`/var/witty-ub/classifier-runtime` 加载初始模型及提取代码，无需安装前端包。
Docker 的前后端角色共享持久卷 `witty-ub-classifier-models`。跨机必须挂载同一共享文件系统；
各部署路径的配置和验证见[分类器部署说明](../../../../deploy/CLASSIFIER_RUNTIME.md)。目录保存：
`training.json` 状态、`active.json` 指针、`versions/` 模型/参考库、`samples/` 观测缓存、临时 `jobs/`。
后端依赖 `scikit-learn>=1.5,<2.0`；Agent 推理仅用标准库。PostgreSQL advisory lock 保证多个后端不会重复启动训练。
`WITTY_CLASSIFIER_AUTO_TRAIN=0` 可暂停后台训练，默认启用。修改部署挂载或依赖后须重建/重启相关服务。

`GET /diag_case_library/classifier/status` 返回状态；
`POST /diag_case_library/classifier/retrain` 沿用操作人校验用于失败重试。
仓库根 `scripts/fault_label_loo/` 保留离线资源构建及评估流程；生产自动训练由后端调度，报告流程不拟合。
